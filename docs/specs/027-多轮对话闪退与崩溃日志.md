## 目标

用户 2026-11-17 在 Windows 安装版实测："进行多次对话后会崩溃闪退"；补充："图标也没了，整个画面退出。可以确定就是多次对话会退出，我总共发送了6轮消息，在第6轮的时候退出，并且我只发送了1～6六个数字。"

也就是：**聊天窗口连续发 6 条很短的消息（"1"～"6"），第 6 条时整个程序退出，托盘图标也消失**。要做三件事：①加持久的崩溃日志，以后任何退出都能事后看到原因；②在本机复现（假 DeepSeek 服务、连续多轮对话）并找到原因；③修掉，并加一条自动测试防止回归。

## 现状（主导已核实）

- 打包版没有任何持久日志：`app/src/main/index.ts` 里 `render-process-gone` 只 `console.error`（约 412 行），主进程没有 `uncaughtException` / `unhandledRejection` / `app.on('child-process-gone')` 的记录；安装版看不到控制台。
- 主进程退出路径：`app.on('window-all-closed', () => app.quit())`（约 632 行）；`app.whenReady().then(start).catch(... app.exit(1))`（约 600 行）；托盘"退出"菜单。
- Windows 上 `app/src/main/perch/windows.ts` 每 100ms 用 koffi 调 `EnumWindows`（`index.ts` 约 379～403 行的 `stopPerch = setInterval(poll, 100)`）；原生层崩溃也会表现为无声整体退出。吸附功能本身之后由 028 删除，本任务**不删**，只在排查里确认或排除它。
- 用户说"只有 6 轮、只发数字"，所以内存慢慢涨爆的可能性小，更像是某个按对话次数累积的东西（每轮新建而不释放的对象、监听器、窗口、WebGL 资源、子进程），或者第 N 轮触发的某个分支（例如情绪/表情、叫声、自言自语、作息计数达到阈值）。
- 另一个要排查的假设：每轮对话让 GPU 进程崩溃一次，Chromium 在 GPU 进程连续崩溃若干次后会让整个浏览器进程退出（日志里会有 "GPU process isn't usable. Goodbye."）。`child-process-gone` 能看到 GPU 进程的 `reason` 与 `exitCode`。

## 要求

### 1. 崩溃日志（`app/src/main/crashLog.ts`，新建）

- 写到 `app.getPath('userData')/crash.log`，追加写，每行一条：`<ISO 时间> <类别> <JSON>`。文件超过 1 MB 时改名为 `crash.log.1`（只保留一个旧文件）再写新的。写失败只 `console.error`，不能抛出。
- 记录这些类别：
  - `start`：版本号、平台、Electron 版本、是否打包。
  - `main-exception` / `main-rejection`：主进程 `process.on('uncaughtException')`、`process.on('unhandledRejection')`，记录 message 与 stack。`uncaughtException` 记录后保持 Electron 原有行为（不吞掉、不改变退出与否）。
  - `render-gone`：每个 `webContents` 的 `render-process-gone`（窗口名：pet / bubble / chat / settings，`reason`、`exitCode`）。
  - `child-gone`：`app.on('child-process-gone')`（`type`、`reason`、`exitCode`、`serviceName`、`name`）。
  - `quit`：`before-quit` / `will-quit` 时记录触发来源（托盘退出、所有窗口关闭、start 失败、冒烟退出），在调用 `app.quit()` / `app.exit()` 的每个地方先记一行来源。
  - `mem`：每 10 分钟一次 `process.memoryUsage()` 的 rss、heapUsed，以及 `app.getAppMetrics()` 各进程的 type 与 workingSetSize 合计。
  - `chat`：每轮对话结束记一行累计轮数、本轮耗时、是否出错（**不记录对话内容和 API key**）。
- 设置页或托盘菜单**不加**入口；在 `docs/guides/02-安装与使用.md` 写一节"闪退时怎么找日志"：Windows 是 `%APPDATA%\Usagi\crash.log`，macOS 是 `~/Library/Application Support/Usagi/crash.log`（以 `app.getPath('userData')` 的实际值为准，执行者核实 productName 对应的目录名后写）。

### 2. 复现

- 用冒烟里已有的依赖注入方式（`app/scripts/smoke-ui.ts` 的 `smokeDependencies()` 一类）或本地假 SSE 服务代替 DeepSeek，**不要用真实 API key、不联网**。
- 加一条冒烟检查（`npm --prefix app run smoke` 会跑到）：通过聊天窗口的真实 IPC 路径连续发送 `1`～`12` 共 12 轮，每轮等回复完成；全程主进程不退出、所有 `render-process-gone` / `child-process-gone` 计数为 0、12 轮后 `BrowserWindow.getAllWindows().length` 与第 1 轮后相同、主进程 `ipcMain` / `webContents` 上的监听器数不随轮数增长（每轮后记录，第 12 轮与第 2 轮相同）。
- 在 macOS 上能复现就修；macOS 上复现不出（例如是 Windows 独有的原生调用问题）时，照常把日志和防护做完，把可能原因按可能性排序写进汇报，并标出哪些在 Windows 上需要用户用新日志版本确认。

### 3. 修复

- 找到原因后做最小修复，汇报写清"原因 → 证据（复现日志或测试）→ 改法"。
- 如果原因是每轮新建而不释放的东西，修复后按上面的冒烟检查证明不再增长。
- 如果证据指向 koffi / `app/src/main/perch/windows.ts`：本任务只把它改为出错时停用（已有 `fail` 逻辑）并在日志记录，不删吸附功能（028 删）。

## 自测

只跑和改动相关的：`npm --prefix app test -- crash chat ui`（按实际文件名），以及本地跑一次 `npm --prefix app run smoke` 确认 12 轮检查通过。不在仓库根目录跑 vitest（会生成根目录 node_modules）。

开工先跑 `grep -rn "window-all-closed\|before-quit\|render-process-gone\|child-process-gone\|uncaughtException\|app.exit\|app.quit\|chat:send\|chat:appended\|smokeDependencies" app/tests app/scripts app/src`（**不要截断**），完整贴进汇报，逐个说明改不改；改写断言在 `## 断言改写` 逐条写"原 → 新 → 原因"。

## 不做

- 不删吸附功能（028 做）；不改模型、道具、动作、表情素材；不加设置项；不记录对话内容或 key。
- 做不通就停下汇报，不改清单以外的文件；需要别的文件写 `## 需要越界`。
